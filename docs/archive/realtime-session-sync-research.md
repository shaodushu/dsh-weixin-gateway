# 跨进程共享会话实时同步方案调研（2026-08-24）

背景：微信网关（headless profile）与 web（dsh web profile）共享 `__room__` 会话文件
（bind mount），web 端查看微信历史消息的实时同步方案调研。检索方式：codebuddy
websearch + 对 dsh 宿主代码的分析。

## 一、dsh 的官方实时链路

- 会话 = 只追加的 `SessionEvent` 日志（唯一真相源）；projection 把事件折叠成 UI 状态
- 实时链路 = **HTTP 上行（命令）+ WebSocket 下行（推送）**：宿主把 `session/event`
  经 WebSocket 推给浏览器
- 投影注册表订阅一次事件流，把每个提交事件折叠进所有投影单元
- **关键限制**：WebSocket 推送的源是**宿主（web 进程）内的事件流**——网关进程写入的
  事件不产生 web 进程事件，跨进程无法注入（无官方通道）

## 二、同行经验：三层架构（跨进程会话实时同步的标准拆法）

1. **存储层**：共享会话文件（按 seq 追加写 + fsync，读者只读增量）——已具备
2. **通知层**：跨进程通知"有新内容"（当前方案的薄弱点）
3. **交付层**：WebSocket/SSE 推前端——已具备（dsh 宿主自带）

方案定位（别用错层）：
- **WebSocket**：只解决"服务器→前端"交付，不解决网关与 web 两进程间的通知
- **消息队列**（Redis pub/sub / NATS / ZeroMQ）：跨进程通知正解；最佳实践=队列只推
  轻量信号（如"seq 推进到 N"），内容仍让消费者读文件增量
- **信号量/文件锁**：并发安全机制，不是通知机制（追加写+fsync 或写临时文件再 rename）
- **信号文件**：最简 IPC，可用但两个短板：内容只写时间戳无法判断是否有增量；
  秒级延迟，仍需轮询兜底

## 三、落地决策（本项目）

1. **信号文件升级为 seq 信号**：网关每次消息后写 `~/.dsh/room-sync-signal`，
   内容 `room=<id>,seq=<N>`（网关 0.5.13），web 插件比对 seq 有增量才处理
2. **投影缓存刷新**（coldSnapshot）：列表层实时（web 插件 dsh-room-projection-sync）
3. **会话对象刷新**（detachEntered）：**实测不可行**——web 进程无法从插件侧获取
   会话对象引用（attach 历史加载不产生事件、store 无遍历 API）
4. **事件推送**（readFrom 增量 → ctx.emit）：**受阻**——readFrom 底层报错
   （jsonl 后端方法签名差异）+ 同样缺 session 对象引用
5. **兜底**：10 分钟定时重启 web（systemd timer，会话对象重建）+ 30s 轮询 +
   网关 30s 文件自愈

## 四、未解问题与后续方向

- "打开状态下自动推送"需要侵入 dsh 宿主（web 进程监听信号 → 强制会话重载 + emit），
  高风险且被升级覆盖——暂不做
- 若 dsh 后续提供"跨进程事件注入"或"会话对象按 id 查询"的官方 API，可重做推送
