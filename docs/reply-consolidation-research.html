微信网关回复链路调研

微信回复与模型回复,如何合并成一条可读的消息

现状:模型生成一段完整回复,微信侧却收到一堆碎片——部分片段还可能被服务端拒绝,读起来像被"截断"。本文梳理发送链路、确认协议约束,给出聚合发送与可靠性方案。

80 字符 流式发送阈值(硬编码)——一次 500 字回复被切成 6–8 条
≈2048 字符 微信个人号单条文本上限,超限报错拒绝、不静默截断
ret=-2 同 context 高频连发被服务端拒绝——尾部片段丢失 = 用户看到的"截断"

现状:两条链路如何拼成一条对话

模型侧聚合是完整的(会话文件实测:天气回复一字不差落盘),问题全部出在"模型输出 → 微信消息"这一段。

三个根因:"截断"从哪来

可读性低不是单一原因,是三个机制叠加的结果。

01

碎片化

80 字符阈值把一段完整回复切成 6–8 条独立消息,切分位置按换行/单词边界,不按语义段落。微信里看到的是断续的小气泡,结论被拦腰打断。

证据:streaming-sender.ts:42 threshold=80 硬编码
02

高频连发被拒 → 真截断

所有分片复用同一个 context_token 连续发送,服务端对高频复用有限制(腾讯 issue #81:同一 context 连续发多条,后面被拒)。尾部片段丢失,用户看到的回复就是残缺的——且失败 3 次后只有一条兜底提示,不补发。

证据:8/21 日志 2297 个 delta 全挂 ret=-2 prepare failed
03

呈现层打断

占位消息("正在生成图片")、工具卡片、typing 状态与文本交错。图片生成占位发出后,正式回复又以多条碎片抵达,微信里一条对话像三场对话。

证据:driver.ts:404 占位 + reply-progress 卡片默认开启

微信协议约束(调研确认)

方案必须在这些约束内设计——尤其"编辑已发消息"不可用,决定了不能"先流式、后合并"。

约束数值 / 行为来源与备注
单条文本上限 约 2048 字符 社区实测值(非官方文档);超限是报错拒绝,不是静默截断。与企业微信"2048 字节"易混淆
ret=-2 语义 rate limited = 真限流;prepare failed = 消息构造/context 失败;裸 -2 = context 过期 腾讯 openclaw issue #81/#142。区分处理才有意义——token 失效时重试只会持续失败
context_token 配额 约 24h 无用户主动消息即冻结,主动推送全失败 腾讯云社区:每用户每 24h 至少一条入站消息续期。网关 8/21 的 prepare failed 即此症状
发送频率 安全 ≈ ≤8 条/分钟;12+ 条/分钟开始失败 Hermes 防封号经验值(非官方)。当前代码串行发送、无间隔,无退避
消息编辑 / 撤回 不支持。iLink 协议无 update/revoke 端点 决定性约束:发出即定型,只能发新消息。message_state 是接收侧字段

同行开源经验

四路调研:上游官方 openclaw-weixin、wechaty 生态、chatgpt-on-wechat(中文社区最大微信 AI bot)、Telegram/Discord 可编辑平台对照。

项目长回复处理发送节奏 / 限流对我们的借鉴
openclaw-weixin
(上游官方)		 整段一次发,无分片。官方 OpenClaw 核心有 "chunking contract"(渠道级块级发送),但微信插件未实现——issue #165 公开承认"长文本回复缺可靠分块,微信侧易截断/失败" 社区配置模拟人工打字:typing_delay_ms: 850、chunk_size: 8;核心层对 429/超时指数退避重试 官方也没解决,且官方方向就是"块级发送"非逐 token——我们的 80 字符阈值比所有同行的分片粒度都小
wechaty 生态 社区共识:500 字符/段保守分片(社区常用 1500–2000 但越接近上限越易被拒);Unicode 码点切分防劈 emoji/中文;优先在 \n 段落边界切 串行发送 + 间隔 300ms~1s;禁止并发发分片(微信乱序);分片预留余量(字节 vs 字符的坑) 验证了"500 字分片 + 段间间隔"是社区基准;我们的 flush 按行拆 + AGENTS.md 500 字约定与之一致
chatgpt-on-wechat
(最直接对标)		 500 字分片(行优先切,超长单行才按字符切);流式输出是"伪流式"——每段仍受 500 字约束,微信上多条消息蹦出 每会话队列(Dequeue+信号量)串行保序;失败重试 2–3 次带 sleep,永久错误直接放弃;连发间隔 0.5–1s 防"操作频繁" 中文微信 bot 社区大规模验证的路线:聚合到语义块(500 字)+ 队列 + 间隔,而不是碎片流
底层 SDK
(openwechat / gewechat / wechatferry / wxauto)		 全部裸发:ReplyText / postText / send_text,无分片无包装 无限流无重试——分片/限流/重试全部由应用层(CoW)负责 分片、队列、重试是我们网关层的职责,与生态一致
Telegram / Discord
(可编辑平台对照)		 原地更新:先发占位 → edit 同一条,节流 500ms–1s 或 10–20 字 flush;超长切新消息并标注"…接续" edit 限频(TG ~20 次/分,Discord 5 次/5s);markdown 未闭合是最大坑;消息失效 catch 后改发新消息 微信无编辑 → 可编辑方案不可行;对无编辑平台的框架共识是:占位+全量 / 分片增量 / 队列合并 三选一

同行共识:① 微信侧"流式 = 多条消息"是公认事实,但所有成熟项目都做聚合到语义块(500 字级)而非逐 token 碎片;② 发送靠队列串行 + 段间间隔保序防限流;③ 无编辑平台的体验取决于"首条消息多快 + 节奏稳不稳",占位先行是通用第一步。我们当前 80 字符阈值是全部对比项目中最碎的粒度。

方案对比

四个方向不互斥——推荐 A+C 组合落地,呈现层收敛(D)作为配套。

A · 聚合缓冲,一次成文 推荐主方案

生成期间只累积 + 保持"正在输入",agent 完成后统一发送。≤2048 字符直接一条;超长按语义段落拆 2–3 条,段间间隔 300–500ms。

  • 微信里是一条完整消息,阅读性最高
  • 发送次数骤降(1–3 条 vs 6–8 条),不再撞高频限流,"截断"根因消失
  • 同行依据:Telegram/Discord 生态对"无编辑平台"的框架共识第一推荐就是"占位+全量"(nonebot/koishi 等);官方 OpenClaw 的 chunking contract 同样是块级发送
  • 超长回复(实测罕见,模型被 AGENTS.md 约束在短回复)可分段兜底

代价:失去"逐步生成"的流式体验——微信场景下用户看的是完整消息,此价值很低;生成期用户看到的是 typing,长任务(文生图 ~60s)需保留占位。

B · 段落感知分段 + 节流 保守渐进

保留流式:阈值提到 500 字符(与 AGENTS.md、chatgpt-on-wechat 一致),按句号/段落切分,每会话串行队列 + 段间 sleep 0.5–1s(CoW 实测间隔),Unicode 码点切分防劈 emoji。

  • chatgpt-on-wechat 在中文社区大规模验证的路线:500 字分片 + 队列 + 间隔

结论:可作 A 的降级模式(用户偏好流式时),或 A 中超长回复的分段实现——不单独作为主方案。

C · 发送可靠性层 必须配套

与 A/B 叠加,专治"截断"残留风险:

  • ret=-2 分流(api.ts:517 目前一律 throw):rate limited → 指数退避(1s/2s/4s);prepare failed/裸 -2 → 不盲目重试,标记 context 过期,提示"请先给机器人发一条消息刷新会话"
  • 失败补发队列:未送达片段暂存,通道恢复后自动补发(不只发一条兜底提示)
  • 发送前长度检查:>2000 字符强制按段落切;Unicode 码点切分,预留字节余量(含 emoji/中文时 2048 字节 ≈ 700 汉字)
  • 速率控制:每会话串行队列保序(CoW 模式),段间 0.5–1s,峰值 ≤8 条/分钟,超限排队延迟发送;重试 2–3 次带 sleep,永久错误直接放弃
D · 呈现层收敛 配套
  • 工具卡片默认关闭(replyProgressMessages: false),或仅长任务开启——卡片穿插是碎片感的重要来源
  • 文生图占位策略:生成期间发一次"正在生成,约 1 分钟"且聚合模式不叠加碎片;图片到达后一条"画好了:[image:…]"消息收尾
  • AGENTS.md 强化:单次回复目标 ≤1500 字符、必含"结论"首句——从源头控制长度,聚合后天然一条

推荐落地路线

按"改动小 → 见效快 → 再加固"排序,每阶段独立可测可发布。

阶段 1

聚合模式 + 长度保护 + 节流(核心修复)

WeixinStreamingSender 增加聚合模式:流式期间只喂 filter 缓存、不发微信;完成后一次发送(超长按段落切,段间 300ms)。非聚合模式保留现状。

  • 80 阈值碎片 → 1–3 条完整消息,"截断"主根因消除
  • 发送前 >2000 字符强制分段(2048 上限保护)
